# Справка по проекту «Мониторинг ИС» — что сделано в этом диалоге

Эта справка — конспект одного очень длинного разговора по доработке
антипиратского Flask/Python-приложения для юридической фирмы. Не заменяет
`README.md` (общее описание проекта) и `заметки-к-развёртыванию.md`
(деплой) — это карта именно того, что накопилось поверх них.

На момент завершения: **494 теста, все зелёные**, 25 файлов в `backend/`.

---

## 1. Модель дел блокировки — три этапа вместо одного статуса

Раньше было одно поле «Статус». Теперь три независимых решения, у каждого
одинаковый набор значений: `"" | "заблокировано" | "отклонено" | "нет реакции"`
(`storage.APPEAL_DECISIONS`):

| Поле | Этап |
|---|---|
| `claim_decision` | Решение по досудебной претензии администратору сайта |
| `first_appeal_decision` | Решение по первому обращению (в Мосгорсуд + РКН вместе) |
| `repeat_appeal_decision` | Решение по повторному обращению |

Правило: **любой** из трёх этапов = «заблокировано» → дело считается
закрытым (`link_check.is_blocked()`). Если первое/повторное обращение
получило «отклонено»/«нет реакции» — можно сразу готовить следующее
заявление (`link_check.appeal_failed()`), не дожидаясь автоматической
проверки ссылки.

**Даты подачи** — раздельные поля для первой и повторной подачи, не
перезаписывают друг друга:
`petition_filed_at` / `rkn_filed_at` (первая) и
`repeat_petition_filed_at` / `repeat_rkn_filed_at` (повторная).

**Автоматический мониторинг** (`link_check.py`) — через 14 дней после
самой поздней из известных дат подачи (или после `block_date`, если дело
уже заблокировано) фоновый поток проверяет, действительно ли ссылка
недоступна. Если ссылка снова доступна — ставится `needs_resend = True`,
это открывает чекбокс повторной подготовки заявления. **Важно**: если
дело заблокировано, но `block_date` не заполнена — мониторинг не
запускается вообще (не проваливается обратно к устаревшим датам подачи —
это был реальный найденный и исправленный баг).

**Скрытие ненужных столбцов**: если дело закрыто на раннем этапе, поля
последующих этапов (номер определения суда, обращение в РКН и т.д.)
показывают «—» вместо полей ввода — данные не теряются (просто скрыты),
и автоматически появляются снова, если `needs_resend` встаёт (дело
вернулось в работу).

## 2. Каналы отправки требований — у каждого своя логика

| Канал | Поля дела | Особенность |
|---|---|---|
| **Претензия** хостингу | `claim_date`, кнопка ✉️ | Автопроставление даты по клику, если ещё не заполнена |
| **Заявление в суд / РКН** | `petition_filed_at` и т.д. | См. раздел 1 |
| **Google DMCA** | `google_dmca_filed_at` | Доступно только если отмечена галочка «Google» в «В выдаче». Ручная дата — форму Google (`support.google.com/legal/troubleshooter/1114905`) автоматизировать не стали: требует входа в аккаунт и это подписанный юридический документ, риски выше пользы |
| **Avito** | `avito_complaint_filed_at`, `avito_complaint_channel` | Доступно только если отмечена галочка «Avito». Одна кнопка 📢, действие (открыть письмо / открыть `support.avito.ru/request`) зависит от выбора в select рядом. **Честная оговорка**: у Avito нет официально задокументированного канала для жалоб на авторские права — сайт блокирует автоматическую проверку, адрес `support@avito.ru` не подтверждён напрямую |
| **Другое** | `other_complaints` — список | Кнопка-счётчик 📋 открывает модальное окно: можно добавить сколько угодно записей (дата + куда + примечание) на разные площадки (VK, Meta, торрент-трекеры и т.п.) для одного дела |

Тексты писем — **настоящие файлы** в `data/templates/` (например,
`avito_complaint.txt`), не просто запись в JSON-настройках. Формат файла:
первая строка `Тема: ...`, дальше тело письма.

## 3. Журнал отправок (только admin)

Отдельный от общего журнала действий файл `data/complaint_send_log.json`.
Фиксирует **каждый раз**, когда любое из полей дат отправки (претензия,
заявление, РКН — первое/повторное, Google DMCA, Avito, каждая запись
«Другое») меняется на новое непустое значение — включая повторные
отправки, не только первую. Кто, когда, что именно, по какой ссылке —
`GET /api/complaint-send-log`, роль admin.

## 4. Раздел «Аналитика» (только admin)

Три среза по месяцам (`backend/analytics.py`):
1. **Обнаружено** — из журнала действий (запись «добавил в блокировку»),
   работает даже за месяцы до появления этого раздела. Топ доменов.
2. **Заблокировано** — по `block_date`, учитывает и активные, и уже
   заархивированные дела (после «Завершить месяц»).
3. **Динамика** — обнаружение против блокировки на одном графике,
   медианное число дней до блокировки.

Числа можно **поправить вручную** (если автоподсчёт что-то не учёл) —
подсвечиваются жёлтым и на экране, и в скачиваемом `.xlsx`-отчёте.
Графики — свой SVG, без внешних библиотек (сознательно, чтобы не тянуть
CDN-зависимость на сервер без доступа в интернет).

## 5. Отчёты

- **Обычный месячный отчёт** (`Отчёт за месяц (.xlsx)`) — как было.
- **Отчёт по автору с актом** (`GET /api/authors/<id>/monthly-work-report.xlsx`)
  — новый, по образцу присланного пользователем реального отчёта
  юрфирмы: лист на каждое произведение (Ссылка / Претензия / Решение /
  Дата блокировки / Повторное решение / Обращения РКН — читаемые
  предложения, собранные из структурированных полей) + отдельный лист
  «Акт выполненных работ» с реквизитами заказчика, перечнем произведений
  и услуг, стоимостью. Реквизиты заказчика (юрлицо, директор в
  родительном падеже, номер и дата договора, месячная плата) — в карточке
  автора. Реквизиты самой юрфирмы (шапка акта) — в «Настройках».

## 6. Определение IP/хостинга/email ответчика

`backend/netinfo.py` — через `rdap.org` (структурированный JSON,
надёжнее текстового WHOIS). Извлекает реального держателя блока (не
служебный идентификатор регистратора вроде `lir-lv-podacini`) и email по
роли `abuse` в RDAP-ответе.

**Автоскриншот подтверждения** (кнопка 📋 у IP) — сначала пробует
`2ip.io` (русский интерфейс, заполнение формы через Playwright — более
хрупкая автоматизация стороннего сайта), при неудаче — собственная
читаемая HTML-страница-сводка (не сырой JSON) из уже известных данных
дела, без повторного похода в сеть.

## 7. Поиск — множественное выделение и копирование

Во всех трёх таблицах результатов (основной поиск, «Поиск по сайтам»,
сохранённые) — чекбоксы в начале строки + кнопка «Скопировать выбранные
ссылки» (копирует только URL, каждый с новой строки). Отдельно у каждой
строки — «Копировать» (всё вместе) и «Копировать ссылку» (только URL).

## 8. Меню и роли

- **⚙️ Администрирование** — сворачиваемый раздел, внутри: Журнал
  действий, Журнал отправок, Аналитика, Доступ. Всё — только admin, и на
  кнопках, и на самих API-эндпоинтах.
- **🗂 Мои документы** — свои документы сотрудника, автоматически
  прикладываются к заявлению. Просмотр доступен любому вошедшему
  (viewer «видит всё»), загрузка/удаление — только editor+.
- Защита от задвоения дел при параллельной работе нескольких сотрудников
  над одной и той же ссылкой (нормализация URL, отдельный конфликт `409`).

## 9. Известные ограничения (честно, не проверено до конца)

- **Avito** — нет подтверждённого официального канала для жалоб на
  авторские права, адрес по умолчанию не проверен напрямую.
- **2ip.io** (автоскриншот) — структура формы предполагается по
  скриншотам пользователя, не по прямому осмотру HTML сайта.
- **Многопроцессный запуск** (`gunicorn -w >1`) не поддерживается —
  внутренняя блокировка `_lock` работает только в пределах одного
  процесса. Разворачивать строго с `-w 1`.
- **`app.py`** разросся до ~2100 строк — не разбит на Flask blueprints,
  технический долг, накопленный за разговор, но не исправленный.
- Денежная оценка «упущенной прибыли» сознательно не делалась — нет
  реальных данных для расчёта.

## 10. Тесты

**494 теста**, все проходят. Есть специальный тест
(`tests/test_blocking_table_column_order.py`), который сверяет порядок
заголовков таблицы блокировки (`index.html`) с порядком ячеек в
JS-рендере строки (`app.js`) — реально ловил рассинхронизацию несколько
раз за этот разговор, когда добавлялись новые колонки.

Финальный архив с полным кодом — `piracy-monitor-updated.zip`, каждый раз
пересобирается заново при следующем сообщении в диалоге, где что-то
меняется.
