# Заметки к развёртыванию — накопились в процессе доработки функций

Этот файл — не отдельный бриф, а дополнение к уже существующему брифу
«Мониторинг ИС на Яндекс.Облаке». Сюда просто складываются технические
моменты, которые важно не забыть на этапе переноса на сервер, но которые
возникли уже после того брифа, в процессе доработки функций.

## 1. Автоматический скриншот (Playwright) — обязательный шаг после установки

В `requirements.txt` добавлена библиотека `playwright`. У неё есть
особенность: сам пакет Python и браузерный движок (Chromium) — это два
разных шага установки. Одного `pip install -r requirements.txt`
**недостаточно** — после него на сервере обязательно выполнить ещё:

```bash
playwright install chromium --with-deps
```

Без этого шага кнопка «Сделать автоматический скриншот» будет выдавать
ошибку «браузер не найден». Стоит сразу включить эту команду в шаги
настройки окружения (тот же раздел брифа, где venv и pip install).

## 2. Автоскриншот — расход ресурсов сервера (обновлено — теперь фоновая задача)

Каждый клик по «Сделать автоматический скриншот» запускает временный
процесс headless-браузера (Chromium) — на несколько секунд ощутимо
занимает память и процессор, ощутимо больше, чем всё остальное
приложение. На минимальной конфигурации VM, о которой шла речь в
исходном брифе (нагрузка небольшая, расчёт на 1-3 пользователей) —
это не проблема, но если в будущем скриншоты станут делать пачками
или число пользователей вырастет — стоит вернуться к вопросу
конфигурации VM.

**Важное изменение по сравнению с более ранней версией этого файла:**
раньше снимок делался синхронно прямо внутри одного HTTP-запроса (до
20 секунд), и на сервере с одним рабочим процессом (`gunicorn -w 1` —
см. пункт про несколько workers в исходном брифе) это на всё это время
блокировало ответ сервера для вообще всех остальных пользователей —
кто угодно, делающий что угодно в приложении в этот момент, просто ждал
бы. Теперь это исправлено: снимок запускается как фоновая задача (тот
же принцип, что уже был у поиска), а фронтенд опрашивает статус
отдельными короткими запросами. Практический вывод для nginx: **не
нужно** увеличивать `proxy_read_timeout` специально под этот эндпоинт
(если увеличивали раньше под старую синхронную версию — можно вернуть
как было, обычных 60 секунд с большим запасом хватает, каждый отдельный
запрос теперь короткий).

## 3. Определение IP/хостинга (RDAP) — нужен исходящий доступ в интернет

Функция «🔄» у IP-адреса дела делает исходящий запрос на `rdap.org` —
убедиться, что файрвол/группа безопасности Яндекс.Облака не блокирует
исходящие HTTPS-запросы с сервера (обычно не блокирует по умолчанию,
но стоит явно проверить один раз после развёртывания, на реальной
ссылке из блокировки).

## 4. Отправка жалобы через Gmail — серверных настроек не требует

В отличие от пунктов выше, это не требует ничего дополнительного на
сервере — кнопка «✉️ Отправить» просто открывает Gmail в браузере
пользователя со стороны клиента, письмо уходит с его личного аккаунта.
Упомянуто здесь просто для полноты картины — пункт можно пропустить
при развёртывании.

## 5. Хранение — новые файлы рядом со скриншотами

Автоматические скриншоты добавили на диск ещё один тип файлов — HTML-
снимок страницы (`*.html`), хранится в той же папке
`data/screenshots/`, что и картинки. Учесть это в резервном
копировании (пункт 10 исходного брифа) — она уже копирует всю папку
`data/` целиком, так что отдельных действий не требуется, просто
имейте в виду, что объём этой папки будет расти чуть быстрее, чем
раньше (HTML-файлы страниц обычно небольшие, десятки-сотни КБ, но при
активном использовании функции складываются).

## 6. КРИТИЧНО: ключи шифрования — без них данные теряются навсегда

Несколько функций используют шифрование, где ключ хранится в отдельном
файле рядом с данными. **Если файл ключа потерян, а зашифрованные данные
остались — расшифровать их невозможно в принципе, это не баг, а
неотъемлемое свойство шифрования.** Это отдельная категория риска,
отличная от обычной потери файлов — обычный файл можно восстановить из
любого бэкапа `data/`, а вот если в бэкап попали зашифрованные данные,
но не попал файл ключа (или наоборот) — эти данные потеряны безвозвратно.

Файлы-ключи, которые нужно **обязательно** включать в резервное копирование
вместе с остальными данными (все лежат в `data/`, так что обычный бэкап
всей папки `data/` их уже захватывает — просто держите это в уме, не
делайте бэкап выборочно, по отдельным подпапкам):

- `data/.documents_vault_key` — без него не открыть ни один документ
  автора (доверенности, договоры, выписки из ЕГРЮЛ и т.п.) из
  `data/documents_vault/`.
- `data/.author_personal_data_key` — **отдельный** ключ (не путать с
  предыдущим) для файла `data/author_personal_data.json`, где хранятся
  ФИО/паспорт/СНИЛС авторов-истцов для заявлений в суд. Без него эти
  данные теряются навсегда — придётся заново собирать паспортные данные
  каждого автора.
- `data/admin_master_key.json` — мастер-ключ администратора для доступа
  к личным данным сотрудников. Если он потерян, а у сотрудника сменился
  пароль (из-за чего его собственный доступ тоже пропал) — данные
  теряются полностью, восстановить нечем.
- `data/personal_profiles.json` — сами зашифрованные личные данные
  сотрудников (без ключей выше бессмысленны сами по себе, но без них
  тоже нечего расшифровывать).
- `data/.secret_key` — этот при потере не приводит к потере данных, но
  разлогинит всех пользователей разом (это уже было упомянуто в исходном
  брифе).

Практический вывод: после переноса на сервер стоит явно проверить, что
бэкап-скрипт (пункт 10 исходного брифа) копирует `data/` **целиком**,
включая скрытые файлы (начинающиеся с точки — `cp -r` их подхватывает,
а некоторые узкоспециализированные скрипты синхронизации иногда
пропускают dotfiles по умолчанию, стоит явно перепроверить).

## 7. Разовая команда после первого переноса — миграция старых документов

Если на момент переноса на сервер в `data/documents/` уже есть документы,
загруженные до появления зашифрованного хранилища, — один раз после
обновления кода нужно выполнить:

```bash
python -m backend.migrate_documents_to_vault
```

Безопасно запускать повторно (уже перенесённые файлы пропускаются).
Если этого не сделать — старые документы останутся в незашифрованном виде
и не будут видны через обычные эндпоинты приложения (которые теперь
читают только из `data/documents_vault/`).

## 8. Правило «admin только один» и старый способ входа через .env

Если на сервере в `.env` всё ещё задан `APP_USERS` (старый способ входа,
упомянутый в самом первом брифе) — **каждый** пользователь оттуда
автоматически получает роль admin. Правило «в системе может быть только
один администратор» теперь учитывает и этих пользователей тоже (не только
тех, что созданы через приглашения), но проверить стоит вручную один раз
после переноса: если в `.env` перечислено больше одного имени в
`APP_USERS`, по факту администраторов уже больше одного, и это стоит
осознанно поправить (оставить одного в `.env`, остальных — через обычные
приглашения с ролью editor/viewer), а не полагаться на то, что приложение
это автоматически исправит — оно только не даёт создать ещё одного поверх
существующих, но не трогает то, что уже задано в `.env`.

## 9. Архив отчётов — новый файл в data/, тоже часть обычного бэкапа

Появился `data/report_archive.json` — сюда переносятся дела блокировки
после того, как по ним нажали «Завершить месяц и заархивировать» (кнопка
рядом со скачиванием обычного отчёта). Ничего специального с ним делать
не нужно — это обычный (не зашифрованный) JSON-файл, как и остальные,
общий бэкап папки `data/` его уже забирает. Упомянут здесь просто чтобы
не забыть, что дела из активной таблицы «Блокировка» не удаляются
безвозвратно этой кнопкой — они перемещаются сюда, и их можно вернуть
обратно через кнопку «Восстановить» в архиве отчётов автора.

## 10. Тесты теперь не трогают реальную data/ — раньше трогали

Была найдена и исправлена ошибка в тестовой инфраструктуре: часть тестов
(всё, что связано с зашифрованными документами авторов) писала файлы
прямо в настоящую `data/documents_vault/` проекта вместо временной папки,
потому что путь к этой папке вычислялся один раз при запуске приложения,
а не заново на момент теста. Если после `git pull`/обновления кода вы
когда-то запускали `python -m unittest discover -s tests` прямо в папке
с реальными данными — стоит одним глазом проверить `data/documents_vault/`
на предмет тестового мусора (файлы с именами вида `test_*`, `file_0.pdf`
и т.п.) и убрать, если найдётся. На момент этого обновления заметок
никакого мусора там не оставалось (проверено), но для более ранних
прогонов тестов, если они у вас были, гарантии нет.

## 11. Новый фоновый поток — проверка доступности ссылок

Добавлена функция: через 14 дней после того, как сотрудник отметил
заявление как поданное («Подано DD.MM.YYYY» рядом со ссылкой), приложение
само проверяет, отвечает ли ещё сайт по этой ссылке — обычным HTTP-
запросом раз в час (без выделенного cron, простой демон-поток в памяти
процесса, тот же принцип, что и у остальных фоновых задач). Есть и кнопка
«🔄 Проверить сейчас» — не ждать часового цикла.

Для развёртывания это означает одну вещь: у процесса `gunicorn` теперь
всегда есть один дополнительный лёгкий фоновый поток, живущий столько же,
сколько сам процесс. Ресурсов почти не потребляет (раз в час — простой
GET-запрос на каждую «созревшую» ссылку, не одновременно все сразу), но
если процесс перезапускается (деплой новой версии, падение и рестарт
через systemd) — поток запускается заново автоматически при следующем
импорте `app.py`, никаких дополнительных действий не требуется.

## 12. Восстановление доступа, если единственный admin потерял пароль

Появился аварийный скрипт — на случай, если у admin (по правилам
приложения он один) пропал доступ: забыл пароль, уволился без передачи,
или ошибся при смене. Запускается прямо на сервере, требует доступа к
файловой системе (то же доверие, что и у `migrate_documents_to_vault.py`):

```bash
python -m backend.reset_admin_password ИМЯ_ПОЛЬЗОВАТЕЛЯ
```

Спросит новый пароль дважды (не в аргументах командной строки — чтобы не
осел в истории shell). Если в системе не осталось ни одного
администратора вообще — покажет команду для создания нового:

```bash
python -m backend.reset_admin_password ИМЯ_ПОЛЬЗОВАТЕЛЯ --create
```

Важно: это НЕ восстанавливает доступ к зашифрованным личным данным
авторов и документам — те защищены отдельными файлами-ключами на диске
(пункт 6 выше), не паролем admin. Сброс пароля их не трогает и не ломает.

## 13. Предел собственных тестов для интеграций со сторонними сайтами

Нашёл на практике: автоматизация формы `2ip.io` (кнопка 📋 — подтверждение
хостинга) у меня в тестах проходила зелёным, а на реальном сервере
реально зависала — потому что мои тесты используют упрощённую локальную
тестовую страницу без рекламы/счётчиков, которая физически не может
воспроизвести поведение настоящего сайта. Зафиксировано и починено (см.
предыдущую переписку про `networkidle` → `domcontentloaded`), но сам
принцип стоит держать в голове: **для любой новой автоматизации стороннего
сайта — "тесты зелёные" не означает "точно заработает в бою"**. Такие
функции обязательно нужно проверять на реальном сервере с реальным
доступом в интернет, а не полагаться только на локальные тесты.

## 14. Автоматический скриншот при «постоянно блокируемом» домене — отключено (16.09.2026)

Раздел «Скриншоты» скрыт в интерфейсе (кнопки и колонка), а его
автоматический фоновый триггер (запускался сам, без кнопки, при каждом
новом повторе «постоянно блокируемого» домена) — отключён в коде
(`_maybe_auto_capture_chronic` в `backend/app.py`, тело закомментировано,
функция оставлена как есть). Именно эта автоматика (открывала headless
Chromium в фоне незаметно для сотрудника, иногда сразу по нескольким
старым ссылкам группы) была главной причиной падений сервера и 100%
нагрузки на минимальной VM.

Для развёртывания это означает: `playwright install chromium --with-deps`
на сервере больше не обязателен для нормальной работы (Chromium сейчас
никогда не запускается сам), но сами ручные эндпоинты скриншотов в коде
никуда не делись — если решите вернуть функцию позже, шаг снова
понадобится.


## 13. Обращения МГС/РКН списком, проверка ссылок через прокси (23.09)

Подробная инструкция установки — в файле `ОБНОВЛЕНИЕ-23-09.md`. Коротко о
том, что важно для сервера:

- **Разовый перенос данных**: `python -m backend.migrate_appeals` (диагностика),
  затем `--apply`. Выполнять при ОСТАНОВЛЕННОМ сервисе: хранилище на JSON
  защищено блокировкой только внутри одного процесса, параллельная запись
  скрипта и сервера может потерять изменения.
- **Новая переменная `.env` — `LINK_CHECK_PROXY`** (необязательная). Если
  сервер стоит вне России, проверка доступности ссылок без российского
  прокси бессмысленна: блокировки РКН на зарубежный сервер не действуют.
- Старые поля обращений (`court_ruling_number`, `rkn_number`,
  `first_appeal_decision`, `repeat_*`) не удаляются, а поддерживаются как
  копия нового списка `appeals` — откат на прежнюю версию возможен без
  потери данных.
- Добавлять сайты в справочник теперь может любой редактор; временные
  разрешения нужны только для изменения и удаления.
